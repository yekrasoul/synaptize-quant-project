Baseline: `4c54cbe7038c0d273050668cbf884ea409b57251`.

## Decision

**BLOCKED.** `runtime_execution_policy.yaml` remains `execution_enabled: false`
with its kill switch active. No live endpoint was invoked to produce this
report.

`VenueCircuitBreaker` is the owned operational health state provider. Its
deterministic failure/degraded/open/recovery transition tests are VERIFIED,
and Risk consumes its current state separately from the kill switch. Confirmed
V2 accounting persistence and the unified monthly-spend projection are
VERIFIED; they are not current activation blockers.

**Capability parity is VERIFIED in tests:** a supplied safe RiskContext and
VenueAdapter exercise the same shared `plan_pre_submit` boundary used by
ExecutionService, and Shadow stops before a claim or POST. **Operational
Production Shadow parity is PARTIALLY VERIFIED:** its current runtime has no
safe authenticated account/venue context, so it correctly emits
`NOT_VERIFIED / FRESH_ACCOUNT_AND_VENUE_CONTEXT_UNAVAILABLE` rather than
fabricating those facts. This remains an activation blocker.

## CCXT request-construction evidence

`test_ccxt_wire_boundary.py` uses the installed CCXT Bybit implementation,
not a replacement mapper. It fixes only the account-mode read result and
replaces CCXT's final `privatePostV5OrderCreate` method with an in-memory
recorder. The test proves one `ExecutionService` execution reaches exactly one
CCXT-generated request with `symbol=BTCUSDT`, `category=spot`, `side=Buy`,
`orderType=Market`, quote `qty=25`, `marketUnit=quoteCoin`, `isLeverage=0`,
and the canonical identity as `orderLinkId`. A duplicate execution identity
does not reach the recorder again. The same boundary classifies CCXT
`InvalidOrder` as `REJECTED` and timeout as `AMBIGUOUS`, with no re-submit.

This is **VERIFIED pre-network request construction**. The generated-method
name indicates CCXT's intended Bybit V5 order-create binding, but the exact
signed HTTP request method/path/body encoding and signature-dependent headers
remain **NOT VERIFIED** because proving them would require safe credentials
and a controlled signing/wire capture. Therefore
`bybit_ccxt_request_mapping` remains **PARTIALLY_VERIFIED**, and this work
does not authorize cutover.

## Canonical durable evidence

`execution_record_v2` is the schema-validated, secret-free projection of the
durable OMS record. It carries canonical/client identity, decision and
strategy linkage, venue/market/account/environment identity, lifecycle,
claim state, submission timestamp when observed, normalized acknowledgement,
venue order identity, normalized fills/fees, ambiguity/rejection and
reconciliation references/outcome.
The repository remains the single mutable lifecycle source; the immutable
artifact is an audit projection, not a competing state machine.

Accounting follows only `venue fill evidence -> reconciliation -> CONFIRMED
ExecutionRecord -> LedgerEntry`. It is idempotent by confirmed execution
identity and never posts acknowledgement-only data. Historical JSONL ledger
records remain immutable/readable and continue to supply V1 monthly-spend
projection.

## Removal criteria

Legacy submitters/reconcilers may be removed only after all checklist entries
in `config/v2_activation_checklist.yaml` are `VERIFIED`, a controlled
non-production account proves final wire/response parity, and routing leaves
exactly one reachable production network-write path. Historical schema readers
are not removal candidates merely because current code no longer emits them.

`execution_record_v2` limits its market field to `BTC/USDT:spot` only because
that is the current production canonical scope. It is not a permanent Core or
multi-venue domain constraint.
